## LUNE-DEC-001：公开需求与真实用户数据的边界

| 字段 | 内容 |
| --- | --- |
| 决策编号 | LUNE-DEC-001 |
| 决策日期 | 2026-10-30 |
| 决策背景 | 当前在公开 GitHub 仓库开展需求调研并记录产品需求 |
| 问题描述 | 公开需求摘要的授权是否涵盖真实用户资料及未来运营数据 |
| 备选方案 | 仅公开需求和脱敏研究结论；或扩大公开范围。发起人明确选择前者，后者未获授权 |
| 最终决定 | 只公开项目需求及脱敏调研结论，调研参与者和未来真实用户的数据不得公开 |
| 决策原因 | 发起人明确要求保护用户内容；需求公开与用户数据公开是不同事项 |
| 可能影响 | 后续研究、测试、演示、Issue 和日志检查均须遵守；示例使用虚构内容，真实用户数据不得进入公开记录。当前不据此提前设计技术架构 |
| 确认人及依据 | 项目发起人，本次对话明确说明“只能公开需求，后续产品上线用户的东西不可公开，我们现在只是在调研” |

## LUNE-DEC-002：比赛版以记忆和角色连续性为基础

| 字段 | 内容 |
| --- | --- |
| 决策编号 | LUNE-DEC-002 |
| 决策日期 | 2026-10-30 |
| 决策背景 | 长期愿景覆盖记忆、人设、双向交流和主动陪伴，两天比赛版需要收敛验证重点 |
| 问题描述 | 比赛版首先让用户感受到哪种核心价值，以及如何限定主动陪伴范围 |
| 备选方案 | 体验 A：记得用户并保持角色连续性；体验 B：用户不先开口时的主动关心；以 A 为基础并加入有限 B 场景 |
| 最终决定 | 采用 A 为基础、限定一个 B 场景体现双向感；B 使用固定时段问候这一类场景，可通过早安、晚安形式呈现 |
| 决策原因 | 发起人明确选择该组合；以记忆、个性化回应和人设为基础，同时保留日常被主动关心的体验入口 |
| 可能影响 | 主动陪伴暂不扩展为复杂的自主时机判断或多场景联系。固定问候不能等同于完整双向交流；具体时刻、渠道和离线触达可行性仍待后续阶段确定，不能用“打开后才显示”未经说明地替代预期。此决定不代表已完成需求验证或阶段验收 |
| 确认人及依据 | 项目发起人，本次明确选择“A 作为基础，限定一个 B 的场景体现双向感”，并提出早上固定早安、晚上固定晚安等形式 |
