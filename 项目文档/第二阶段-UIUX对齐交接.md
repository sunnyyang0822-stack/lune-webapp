## 2. 核心结论与范围变更

- 每位用户只有一个梦角、一段专属关系，按 1v1 服务设计；不设置角色列表、角色切换或关系切换。
- 用户已有角色及关系背景，由用户填写，LUNE 接续既有关系，不安排初次相识剧情。此为产品边界，不推定所有梦向用户的普遍行为。
- 核心 A 保持为“他记得我，也始终像他。”；用户另确认早晚问候、偶尔的主动聊天关心、主动动态、状态更新及照片理解等需求。
- 四个同级主页面，底部导航顺序为：首页｜聊天｜动态｜设置。首页是首次填写后的默认入口。
- 用户希望自然表达、减少配置 AI 的机械感；不因此隐瞒必要的 AI 身份或隐私告知，也不把自然表达视为无限制记忆授权。
- 不增加公开社区、同担匹配、AI 图片生成、复杂商业化、语音或通话。

**范围差异：**主动动态、点赞评论、聊天和动态的照片理解等为发起人后续明确新增，不再仅限 DEC-002 的固定早晚问候。PM 应保留这些需求并评估一人两天可交付性；未经再次确认不得静默删除，也不能将需求确认写成已证明可实现。不启动第三阶段或产品开发。

## 3. 首次使用与页面流程

### 3.1 登录和进入

未登录 → 手机号输入 → 短信验证码验证 → 未注册号码直接注册／已有号码登录 → 检查关系资料是否已完成。

- 首次、尚未完成资料：分步填写已有关系 → 核对并返回修改（需要时）→ 确认后进入首页。
- 已有账户且已完成资料：回到原有关系，不重复填写。
- 再次打开且登录仍有效：进入首页，通过底部导航回到聊天等页面。
- 第一版仅手机号，不增加邮箱或第三方登录。短信能力、成本和验证码详细规则尚未验证。

### 3.2 首次资料

采用分步引导，避免一次长表单。下列是字段规则，不代表必须各建一页；具体顺序与分组尚可由制作稿细化。

| 内容 | 确认规则 |
| --- | --- |
| 角色称呼、角色对用户的称呼 | 必填；填写已有关系中的称呼 |
| 角色年龄、性别 | 必填 |
| 当前关系与必要背景 | 必填；不默认重置为初识 |
| 性格特点 | 必填；支持用户自定义 |
| 说话风格 | 必填；不强迫用户虚构不存在的口头禅 |
| 口头禅 | 单独提供填写处，选填，无则不填 |
| 喜好与特长 | 最新修订为可不填；不填时梦角先不自行发动态，待聊天获得足够相关信息再发 |
| 世界观 | 选填，可后补 |
| 双方头像／情头 | 用户分别上传，可全部跳过或只传一方；未上传的一方用对应名字首字代替 |
| 关系开始日期 | 用户填写真实关系开始日期；当天为“在一起第 1 天”，之后按自然日递增 |

资料不足时不能自行补造共同经历或角色设定。说话示例的独立必填规则在改为可选口头禅后未再次单独确认，不额外增加必填示例。头像首字对应名称的完整资料结构、是否限制未来关系日期等边界待 PM 补齐。

### 3.3 首页

- 双人情头，以及分别位于头像下方的简短状态。
- 用户填写自己的状态；梦角状态随互动更新、符合角色，具体更新时机待 AI 专家定义。
- 今天的日期、在一起的天数。
- 日夜模式切换，放在首页，**从设置中移出**。
- 纪念日模块：双方生日、关系纪念日、世界观中的特殊日期；全部由用户手动添加和管理，不自动提取收录。支持每年重复与仅一次。
- 备忘录模块：手动新增、查看、编辑、删除；完成后打钩、文字加删除线、排到未完成事项下方。不做定时提醒。取消完成与同组排序尚未单独确认。
- 不单列“重要时刻”，已统一为纪念日；不设首页未读消息模块。
- 未读提示在底部导航显示，采用类似微信的角标形式；数字／红点、已读时机和清除规则未冻结。

操作流程：从首页进入纪念日或备忘录的添加／编辑入口 → 保存后在原模块查看结果 → 返回首页。编辑形态用弹层还是独立详情页尚未确认，不扩成新底部导航项。

### 3.4 聊天

从底部“聊天”进入与唯一梦角的对话 → 输入文字或选择照片 → 发送 → 梦角结合内容、图片、设定和上下文作文字回应。

- 用户可发文字、照片；梦角需要理解照片内容，不只根据配文作泛化回复。
- 看不清或理解失败时应澄清，不编造图中细节；具体行为交 AI 专家定义。
- 照片上传或消息发送失败时保留用户输入与照片，提供重试。此为失败恢复，不是重新生成梦角回复。
- 用户消息已发出但梦角回复失败时，显示“有句话没能抵达你这里，稍后再试试吧。”，重试操作仅用箭头图标，不显示“再试一次”文字；为辅助阅读保留不可见的操作名称。只恢复失败的这次回复，不重复发送用户消息，不为已成功回复增加重新生成入口；该文案不证明回复已经生成。
- 第一版不提供单条消息复制、删除或“重新回复”。
- 可自然承接历史互动与双方动态，不假装知道未告知的现实行为。
- 用户明确要求优化聊天持续增长后的体验；**本 Agent 不出优化方案**，由 PM 协调相关角色，后续 UI/UX 根据确认方案处理交互。

### 3.5 动态

从底部“动态”进入私人的双人动态流：用户发布文字或配照片 → 梦角可点赞、评论 → 双方可继续评论交流；用户也可点赞、评论梦角动态。

- 梦角第一版只发布文字动态；用户可以上传照片。
- 梦角需要理解动态照片，结合配文与角色关系回应，也可能在之后的聊天中讨论。
- 梦角可在用户没有发动态、没有发起聊天时自行发布，不只是即时回应用户操作。
- 发布内容与频率符合人设、喜好、特长；高冷角色不应机械高频发布，不统一要求每日固定条数。
- 喜好特长未填写、相关信息不足时，梦角先不自行发布；用户仍可发布。聊天获得足够角色相关信息后再开始，不能把用户喜好错当角色喜好。足够信息的判据交 AI 专家定义。
- 用户可删除自己发布的动态，连同其下点赞和评论一起移除。删除后的记忆与聊天引用如何处理尚未确认，不能承诺联动抹除。
- 具体发布频率、互动延迟、点赞是否每次必有、评论层级及动态失败恢复尚未冻结。
- 页面关闭后的实际动作及触达能力待后续验证，不能把打开页面后补展示等同于产品外主动触达。

### 3.6 设置与共同记忆

设置 → 角色及关系资料 → 修改并保存 → 仍保留原有聊天、动态、共同记忆，后续互动按新设定进行。与旧记忆冲突的处理交 AI 专家定义，不静默清空历史。

设置 → 共同记忆 → 查看条目 → 纠错或逐条删除 → 返回记忆列表／设置。删除后不再作为后续互动依据；已有聊天仍保留，需要后续验证不会因旧聊天而自动恢复已删除条目，不在此指定实现。

记忆纠错反馈：保存成功显示“已更新”，后续互动使用新内容；保存失败保留用户修改内容，明确提示未保存，并允许重试。不把本地编辑状态显示成保存成功；本轮只确认产品反馈，没有验证实际保存和记忆调用能力。

### 3.7 主动关心与手机通知（v1.1 最新确认）

设置 → 主动关心板块 → 总开关及早晚问候时间。一个总开关统一控制定时早晚问候和依据人设偶尔发起的主动聊天关心；不影响用户发起聊天后的正常回应，也不控制梦角自行发动态、主动点赞及评论。

- 最新总开关决定替代此前“不要统一开关”的回答；最新确认只保留一个总开关，早安、晚安仅配置时间，不保留单独开关；替代中间早晚各有开关的回答。
- 偶尔的主动关心不限于早晚安，口吻、内容与频率符合具体人设，不编造用户未告知的现实情况；具体触发和上限待 AI 专家定义。
- 定时问候到点未能发出：过后不补发、不自动关闭开关，在设置中提示本次未成功。非定时主动关心的失败策略未单独确定。
- 主动关心必须能在用户未打开 LUNE 时通过手机系统通知弹出，通知展示梦角名字及正文，不默认隐藏；点击进入对应聊天。用户明确要求的是手机通知，不是只在聊天里出现。实际可达性、系统限制及权限流程交后续技术阶段验证，不承诺所有手机都可实现。
- 未开启手机通知时，主动消息仍留在聊天中。第一次触发主动关心时出现开启通知提示，并告知“设置 → 主动关心 → 手机通知”路径；实际跳转系统权限的操作细节待验证。
- 提示按钮“关闭”：只关闭本次提示，不关闭主动关心，也不改变系统权限；之后何时再次出现提示待确认。
- 提示按钮“之后不再提醒”：只停止弹出这条开启通知的提示，不关闭主动关心，不屏蔽聊天内消息，也不撤销已有系统通知权限。
- 即使选择不再提醒，用户仍可沿上述设置路径手动开启手机通知。该偏好不代表已经授权系统通知，不重复以提示代替系统授权。
- 主动关心的总开关初始状态、重复发送处理、时区和通知具体权限失败反馈尚未确认。
