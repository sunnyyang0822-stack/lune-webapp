## 第一轮：先检查前置条件

先阅读根目录 AGENTS.md、README.md，以及项目章程、需求分析、品牌规范、项目决策记录和上述两个 Issue。检查 Git 状态，保留已有工作。

当前第三阶段只是预建任务，等待第二阶段验收。必须检查是否有发起人明确验收记录、已确认的 PRD、用户流程和验收条件，以及对应版本。视觉方向确认或 UI 草图完成不等于第二阶段全部验收。

若前置未满足：

- 只读熟悉资料，提交“已有技术约束、仍缺的产品输入、需要产品阶段澄清的问题”简报。
- 可指出需明确的记忆控制、角色来源、问候时间与页面关闭后的触达预期，不提前决定答案。
- 不写正式技术方案，不确定技术栈、模型供应商或基础设施，不设计数据库、API，不写代码或部署。
- 一次只向发起人提出一个最影响方案的问题；已有资料能回答的自己查，不重复提问。
- 简报完成后等待 PM 提供第二阶段验收依据及启动通知，不把本提示词或 Issue 创建当作验收。

## 前置验收满足后：正式开展技术方案设计

按 Issue #3 的技术方案范围执行。先列明所依据的 PRD 与流程版本，区分已确认需求、技术建议和待验证前提。

比赛版一人两天，优先手机友好 Web App。核心是记忆、个性化承接和角色连续性；有限辅助是固定早安／晚安问候，不扩展复杂自主联系、公开社区、图片生成或商业化体系。

提出两到三个合理备选，给出适合比赛的最小可行推荐、取舍和成本。不因追求先进加入不必要组件，也不预设必须使用向量数据库或特定框架。

技术方案应覆盖：

1. 系统组件、责任边界、关键处理链路和应用运行方式。
2. 角色约束、记忆形成和调用、现实与剧情区分、纠错、过期和删除传播的处理策略；与 AI 专家明确职责，不承诺永不遗忘或绝无 OOC。
3. 早晚问候的时间、时区、生成与触达链路，前台、后台、页面关闭状态的能力限制，通知授权、重复执行防护和失败处理；不得悄悄改成仅打开后展示。
4. 身份、用户隔离、密钥保护、第三方模型数据流和最小日志；真实用户梦设、聊天、生活习惯、口头禅与记忆不得进入公开仓库、Issue 或演示材料。
5. 性能、可靠性、费用上限、故障降级、部署回滚和后续测试验证建议。核查当前官方文档、平台限制及版本，记录来源与日期；未做的验证如实标明。
6. 两天内的可行性、实现风险及后续数据模型、API 和任务拆分阶段需要遵守的约束。

发现产品要求不可行时，说明原因、影响、备选及代价，交 PM 和发起人决定；不得自行删改体验或扩大范围。
