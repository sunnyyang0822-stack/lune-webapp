### 1.2 确认状态与评审用语

- **已确认规则**：来自 E2／E3／E6 最新决定或本轮明确边界。确认需求不等于实现。
- **安全建议**：本文提出的控制、告知或验收细化；即使写为“应／不得”，也不冒充发起人已批准的新产品规则。
- **待决定**：影响用户可见行为、用途或删除承诺，交 PM 组织专业意见并由发起人确认。
- **待验证**：后续阶段须用证据验证的能力，不能靠文案或模型自称保证。

## 3. 用户隔离与访问边界

已确认：每用户一个梦角、一段关系；UX-US-01 明确不出现他人资料，AI-REL-06 明确不混入他人内容。四个页面都是同一私人空间，动态不构成公开社区。

建议写入验收基线的隔离要求：

| LUNE 场景 | 后续必须验证的边界 |
| --- | --- |
| 登录后首页、首次资料和设置 | 当前账户仅能看、改自己的角色、关系、状态、日期、纪念日、备忘录及通知偏好；新账户不承接上一账户的本地草稿或默认关系 |
| 聊天历史、照片、动态、评论、头像 | 查看、直接打开链接、修改、删除、重新加载和失败重试均须检查归属；知道链接或内容编号不构成访问授权；“一个角色”不自动证明用户隔离 |
| 共同记忆及角色生成 | 只能用当前账户获准且未被删除限制的信息；对话、图中文字或角色台词要求读取别人内容时也不能改变归属与授权 |
| 通知内容与点击 | 内容及投递目标须属于同一账户；未登录先进入登录流程，账户不匹配不得展示原通知关联的聊天、照片或记忆。重新登录后核对归属，不凭点击链接跳过检查 |
| 同一手机退出甲、进入乙 | 页面返回、刷新、浏览器历史预览、待发送内容、失败重试和延迟通知均不能把甲的私人内容显示给乙；已到系统通知中的旧预览另见 §5，不虚称可以撤回 |
| 运行与人工排障 | “私人”不等于服务处理方完全无法接触内容；如后续需要管理访问、客服或诊断，应先说明必要性和授权边界，不默认所有维护者可浏览用户内容 |

以上是后续要求，尚无实现或测试证据。隔离不能只靠 AI 规则、前端隐藏按钮或难猜链接保证；第三阶段获准后须分析实际访问控制的可行性。

## 4. 记忆、删除与重新授权

### 4.1 已确认规则与未决边界

| 用户动作 | 已确认结果 | 不应混淆的范围／本次建议 |
| --- | --- | --- |
| 查看共同记忆 | 可查看条目 | 按 DEC-009 仅有限自动采纳；来源、主体、现实／剧情与有效时间的可理解说明及实际采纳能力仍待验证 |
| 在设置纠错并保存 | 成功显示“已更新”且后续用新内容；失败保留修改、提示未保存并可重试 | 保存失败不能报成功；聊天中口头纠正是否持久同步是未决项，不替代保存证据 |
| 删除一条记忆 | 条目删除，后续互动不得以该内容为依据；旧聊天保留，不得由其自动恢复条目 | 不只禁止逐字提起，也覆盖同义引用、隐含个性化及动态、评论、状态、问候。建议说明“不再用于后续互动，历史聊天仍保留”；不说所有照片、聊天、备份已清空 |
| 重新浏览含该事实的旧聊天 | 旧原文仍可见 | 阅读历史不是重新授权。旧摘要、旧输出或模型自己记起均不得恢复使用 |
| 删除后再次谈到同一话题 | 重新记住的操作尚未确认 | 建议允许就当次明确输入回应，但不得据此长期恢复；需明确重新授权及反馈。不能将“你还记得吗”、重复发图或点赞当恢复许可 |
| 删除用户动态 | 该动态及点赞评论移除 | 按 DEC-008 分来源处理；不宣称原图、第三方副本或所有关联已删除 |
| 修改角色关系资料 | 旧聊天、动态、共同记忆保留，后续按新设定 | 不静默重置关系；新旧事实冲突建议按 AI-REL-04／05 区分时间与纠错，但 D 项仍需 PM 纳入基线 |
| 注销账户 | DEC-013 已确认二次确认、范围说明及第三方副本边界 | 具体删除／保留清单、期限、失败反馈、跨设备与再注册规则仍缺；不能套用“删一条记忆”的保留策略 |

删除与纠错成功还需覆盖操作时已在生成或等待发出的回复／通知：否则用户刚删除，旧内容仍可能从在途动作泄露。建议 PM 明确用户操作生效时点和可见反馈；技术阶段评估能达到的保证，不能只展示列表变化。

### 4.2 动态删除的影响与推荐方案（未确认）

推荐与 AI P-01 同向：删除动态和互动后，不再从该已删来源新增记忆或主动引用；仅从该来源采纳的记忆同步停止用于后续互动。独立通过其他来源明确确认过的相同事实，单独说明是否保留；旧聊天原文可见性、聊天中照片副本与后续调用分别决定，不能用一句“已删除”覆盖所有项目。

若只移除动态展示，工程范围可能较小，但角色继续谈论已删内容容易违背用户掌控预期，必须明确告知且获得产品决定；若连所有关联事实与历史副本一并清除，范围更大，也可能误删独立来源的经历，并与聊天无单条删除入口的既有决定冲突。推荐方案仍需评估来源区分是否可行；不得在没有能力证据时承诺全量抹除。DEC-008 已形成产品决定；PM 需将其转为逐项可验收范围，不由安全 Agent 擅自扩大删除功能。

## 5. 照片、主动关心及通知专项

### 5.1 照片用途与第三方处理

已确认聊天、用户动态中的照片理解；没有授权公开、二次创作、图片生成、辨认真实身份或推测敏感信息。双方头像上传的功能依据是私人展示，不能直接扩成身份分析。

建议在首次发送照片及后续可找到的说明中，区分“为了回应本次分享而理解”“可能形成记忆”“可能交由第三方处理”。不默认自动形成记忆。提醒用户留意门牌、证件、屏幕、镜面反射及其他人物等背景；可提供发送前检查或重新选图的保护方式作为备选，不宣称会自动消除全部敏感信息。理解失败、发送失败、删除动态、删除记忆与删除原图分别反馈。

第三方服务尚未选型。后续应逐项核查并保留所选服务的官方条款版本、访问日期及适用产品／套餐，不编造供应商政策：

- 实际发送的是原图、配文、角色设定、聊天还是必要片段；头像是否会送出；不为理解一张图默认发送全部历史。明确短信、文本模型、图片理解、通知服务分别接触什么。
- 是否保留原图、输入输出及诊断载荷，保留多久，是否有人审阅、训练／改进用途及可用控制；不把“付费”或“API”自动等同于不留存、不训练。
- 处理位置、转委托方与必要告知；如存在地域或适用规则问题，后续再核查，不在本报告作法律认证。
- 删除、停止处理和相关副本处理能力及限制；账户注销能否覆盖供应商留存，无法覆盖时如何告知。
- 图片访问保护、非公开用途、背景／元数据处理及最少传递；图中文字、配文或历史内容不能充当改变规则、越权读取或上传其他用户内容的指令。
- 服务失败与重试是否额外重复传递照片；成功回复无重生成，失败回复的恢复也须核查必要传递范围与记录边界。

### 5.2 三种控制分别判断

### 5.3 姓名正文通知的暴露风险及点击边界

保留已确认的默认展示梦角名字与正文。风险是锁屏、通知中心、共享设备及系统允许的镜像／配对终端可能让旁人看到私人称呼、关系和消息细节；即使正文不含姓名，也可能由具体经历识别用户。终端表现需实测，不假定所有手机相同。

建议在通知开启说明中明确提醒这一点，并给出通过手机系统管理锁屏预览的指引。可另提“由用户主动选择隐藏正文”的产品备选，但新增偏好是否纳入 MVP 必须另行确认；本轮未将默认改成中性内容，也未认定用户已接受变更。用户上传照片或选择“不再提醒”均不等于接受全部锁屏暴露。

通知点击回对应聊天的已确认路径须保留，同时检查当前账户归属；未登录或错误账户不能先展示私人内容再补登录。已在系统通知中出现的名字正文不由产品内访问检查自动消失，风险告知和后续清理能力须分开说明。

证据须分别标明生成、聊天可见、通知投递、手机实际显示和点击后的访问结果。不用打开页面后展示消息、服务接受请求或截图中的模拟通知冒充实际送达；没有证据不称已读。
