## 3. 候选方案比较

| 维度 | 方案 A：单仓库全栈（Next.js + 托管 Postgres） | 方案 B：前后端分离（Vite SPA + 独立 API 服务 + 容器） | 方案 C：BaaS 快速搭建（低代码／托管后端） |
| --- | --- | --- | --- |
| 交付速度（两天） | 快。一个仓库、一种语言、一条部署命令 | 慢。两套构建、CORS、双部署 | 最快，但定制与调试受限 |
| 一人零基础可维护 | 好。AI 编码工具对此栈最熟 | 一般。需理解两套运行与联调 | 好上手，但出问题时排查困难 |
| 记忆与删除可控性 | 好。服务端完全掌控 SQL 与过滤 | 好 | 一般，受平台能力限制 |
| 赛道 B"云原生"证据 | 中。可容器化，但默认是托管 PaaS | 强。天然容器化、可水平扩展 | 弱 |
| 赛道 B"Agent 链路"证据 | 好。服务端可显式编排多步并落轨迹 | 好 | 弱，编排空间有限 |
| 移动端首屏与 SEO | 好（SSR） | 需自行优化 | 一般 |
| 主要风险 | 免费层定时与通知限制需核实 | 工期超支风险最高 | 平台锁定、难以满足隐私与删除要求 |

**建议（D）：方案 A 为主体 + 方案 B 的容器化交付物**。理由：核心体验（记忆、删除停用、主动问候）都在服务端，单体全栈能把它做对；同时补一份 Dockerfile 与 docker-compose（应用 + 数据库），把"云原生"从 PaaS 默认能力变成可解释的自主取舍，用于赛道 B 的 15 分。方案 C 不建议：隐私与删除传播的可控性不足，且难以提供 Agent 链路证据。

## 4. 推荐架构

### 4.1 组件与边界

| 层 | 组件 | 职责 | 不负责 |
| --- | --- | --- | --- |
| 客户端 | 移动优先 Web（四页 + 底部导航） | 呈现、输入、状态反馈、Service Worker 注册 | 不直连模型、不持有任何密钥 |
| 应用层 · web | 同步 API 服务（无状态，可水平扩展） | 认证、会话、同步业务编排（S1～S3）、模型调用入口 | 不执行长耗时异步任务 |
| 应用层 · worker | 异步任务服务（可独立重启与水平扩展） | 记忆抽取、状态更新、主动问候定时、通知投递（S4～S6） | 不对外承接用户请求 |
| 任务通道 | Postgres 任务表 + 轮询领取（不引入 Redis／消息中间件） | 传递待执行任务，带幂等键与可见性超时 | 不做业务判断 |
| 编排层 | 显式步骤执行器（见 §5） | 把一次用户请求拆成可观测步骤并落轨迹 | 不决定产品规则 |
| 数据层 | 托管 Postgres | 账户、关系资料、消息、动态、记忆、纪念日、备忘、步骤轨迹、任务表 | — |
| 外部 | 短信服务、文本模型、视觉模型、推送通道 | 按需调用 | 不进入产品逻辑分支 |

**两服务拆分口径（DEC-019）**：把同步链路（web）与异步链路（worker）拆开，是同一次改动的两部分；`web` 无状态可加副本，`worker` 可独立重启或扩容，两者共享同一个 Postgres。**不引入 Redis、不引入消息中间件、不上 K8s**：队列用 Postgres 表实现（带 `FOR UPDATE SKIP LOCKED` 语义的领取方式），部署用 Docker Compose 编排 `web`、`worker`、`db` 三个容器。这样做的目的是用最小代价拿到三个真实可取证的能力：职责分离、无状态水平扩展、故障隔离（worker 挂掉不影响回复）。选型细节属实现阶段，此处只定口径。

密钥只存在于服务端环境变量；客户端零密钥（对应安全冻结版 SEC-07／SEC-13）。

### 4.2 关键数据流（文字聊天）

1. 客户端提交用户消息 → 服务端写消息并立即返回"已接收"。
2. 服务端触发一次编排（§5），装配上下文：角色资料 + 允许使用的记忆条目 + 最近对话窗口。
3. 调用文本模型生成回复。
4. 回复写入并推给客户端（"正在输入中"状态结束）。
5. 异步执行记忆抽取与状态更新（不阻塞回复）。
6. 若命中主动关心或纪念日规则，按 §7 处理。

**设计要点**：回复链路必须与记忆链路解耦——记忆抽取失败不得导致回复失败（对应 DEC-012 的失败语义分离）。

## 5. 编排层：把"单轮对话"变成可观测的多步任务

这是本方案为赛道 B"Agent 能力与任务链路（20 分）"提供证据的核心设计，**不改变任何用户可见行为**（用户看到的仍是即时回复）。

| 步骤 | 动作 | 工具调用 | 失败语义 |
| --- | --- | --- | --- |
| S1 上下文装配 | 读取角色资料、关系背景、最近对话 | 数据读取工具 | 失败即整次失败（可重试） |
| S2 记忆检索 | 按来源与状态过滤，只取"仍在用"的条目 | 记忆检索工具 | 失败降级为空记忆并记录，不谎称"记得" |
| S3 生成 | 按 AI 行为规则 v0.4 生成回复 | 文本模型 | 失败显示既定文案 + 箭头重试（DEC-006） |
| S4 记忆抽取 | 判断是否形成新记忆、是否需纠错停用 | 记忆写入工具 | 失败仅记录，不影响已发出回复 |
| S5 状态更新 | 按 DEC-016 的互动枚举更新角色状态 | 数据写入工具 | 同上 |
| S6 通知投递（仅主动关心） | 按 §7 投递或降级为站内 | 推送工具 | 失败不补发、开关不回滚（DEC-010） |

**执行位置（DEC-019）**：S1～S3 在 `web` 同步执行（用户等待路径）；S4～S6 由 `worker` 异步执行（不进入用户等待）。每次执行在 `agent_step.executor` 记录 `web`／`worker`，用于证明职责分离与故障隔离。

**必须提供的可观测证据**：每次编排落一张步骤轨迹（步骤名、执行节点、开始／结束时间、状态、错误类别、是否重试、幂等键），日志与演示只使用虚构内容。轨迹就是答辩时"任务拆解、工具调用、状态管理、容错恢复"四项的证据来源。

**容错与幂等（对应评分"多步骤任务具备容错恢复"）**：每次请求带幂等键；重试只重放失败步骤；已成功的回复不重新生成（DEC-012）；结果未知先查轨迹再决定，不重复提交。

## 6. 记忆子系统

| 环节 | 设计取向 | 依据 |
| --- | --- | --- |
| 形成 | 回复链路成功后异步抽取；只采纳普通、稳定、非敏感信息 | DEC-009 |
| 展示 | 用户在设置中可查看条目全文与来源类别 | DEC-009、UX-US-09 |
| 纠错 | 保存成功才显示"已更新"，后续按新内容 | DEC-009 |
| 删除 | 逐条删除后停止作为后续依据；旧聊天保留 | DEC-008、DEC-009 |
| 来源追踪 | 每条记忆必须可追溯到来源类别（资料、聊天、动态、纪念日） | DEC-008、安全冻结版 §3.5 |
| 停用传播 | 删除动态或记忆后，检索侧必须过滤停用与失源条目 | DEC-008 |

**可观察性设计**：为了让"删除后不再作为依据"能被第三方观察（而非依赖内部状态），检索链路保留可回看的过滤记录（哪条被过滤、因何失败），并在虚拟验收中作为证据。这是"实现层面尽量可观测"，**不等于**保证第三方副本已清除（安全冻结版 §5 已界定不可承诺）。

## 8. 照片理解

链路：客户端压缩与尺寸限制 → 上传 → 服务端转存与临时访问 → 视觉模型识别 → 结果参与生成 → 按策略清理临时文件。

- 首次使用前明确告知第三方处理（DEC-011），告知文案由 UI/UX 交接 v1.2 承载。
- 不确定时澄清、不推断身份或敏感属性（安全冻结版 EV-06）。
- 上传失败与理解失败必须是两种不同状态（前端标注 v0.5 §8）。
- **成本敏感**：视觉模型单价约为文本的一个数量级，须设单次与单日上限（见 §9）。
- 可降级：整条链路可摘除而不影响文字聊天。

## 9. 模型选型与成本、延迟预算

### 9.1 模型（建议 D，待 P-03 确认采用哪一路）

### 9.2 成本估算（推算，非实测）

假设单轮输入约 2.5k tokens（资料 + 记忆 + 近几轮）、输出约 250 tokens：

| 场景 | 单价口径 | 单次 | 演示期总量（估） | 合计 |
| --- | --- | --- | --- | --- |
| 文字对话（V3.2-Exp） | 2／3 元每百万 | ≈ 0.006 元 | 500 轮 | ≈ 3 元 |
| 记忆抽取（小请求） | 同上 | ≈ 0.002 元 | 500 次 | ≈ 1 元 |
| 照片理解 | 16／48 元每百万 | ≈ 0.02 元／张 | 100 张 | ≈ 2 元 |
| 短信验证码 | 约 0.04～0.05 元／条（**需核实**） | ≈ 0.05 元 | 100 条 | ≈ 5 元 |
| **合计** | — | — | — | **≈ 11～15 元，建议预充 50 元** |

**降本措施**：上下文窗口裁剪（只带最近 N 轮 + 命中记忆）；记忆抽取合并为批量或降低频率；照片压缩与尺寸上限；开发期使用固定虚构种子数据，不反复跑真实调用。

### 9.3 延迟预算

| 环节 | 目标 | 说明 |
| --- | --- | --- |
| 文字回复首字 | 1～3 秒 | 取决于模型与上下文长度，**未实测** |
| 记忆抽取 | 不进入用户等待路径 | 异步执行 |

## 10. 两天排期（建议 D）

| 时段 | 工作 | 验收点 |
| --- | --- | --- |
| 第 1 天上午 | 脚手架、数据库接通、认证（见 P-01）、四页骨架与底部导航 | 能登录并进首页 |

**必须诚实的一条**：15 分的"云原生"要求 Docker/K8s、微服务、弹性伸缩、分布式状态。本方案选择"容器化 + 同步／异步两服务拆分 + 托管数据库 + 取舍说明"，属**部分满足**（估 10～12 分），不是完整满足。差额来自不上真实 K8s 集群、不做分布式状态（无 Redis）与不提供压测扩容曲线。若需要更高分，须把工期成本摆到台面上权衡（见 DEC-019 的工时对比）。

**可取证清单（实现后必须真的能拿出）**：① `docker compose up` 起三容器；② `web` 加两个副本的 `docker compose up --scale web=3` 截图；③ 杀掉 `worker` 后聊天仍能回复（故障隔离）的录屏或日志；④ `agent_step.executor` 显示步骤分别落在 web 与 worker。

## 12. 安全与隐私的工程约束（已确认）

1. 密钥只在服务端环境变量，`.env` 不入库；仓库只提供 `.env.example`。
2. 日志最小化：不记录消息原文、照片、记忆内容与手机号；错误日志只记类别与幂等键。
3. 用户隔离：所有查询强制带账户边界；跨账户访问必须返回空而非报错泄露存在性。
4. 公开材料只用虚构数据；演示账号与数据在演示前重置。
5. 删除语义分三层表达：界面移除／停止作为依据／物理副本（第三方不可承诺），不得用"已删除"一词概括。
